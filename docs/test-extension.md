# 测试类型扩展约定

`backend/app/test_catalog.py` 是展示用覆盖目录，不是执行注册表。18 类分类均有被动线索或审查入口，目录统一标记部分支持，不能解释为完整漏洞检测能力。业务逻辑、竞争条件、内存安全及 DoS 等仍需专项证据和验证。目录变更不会启用任何测试。

当前执行模板允许 `baseline`、`role_compare`、`both`、`injection_errors`、`xss_passive`、`csrf_passive` 、`ssrf_passive`、`xxe_passive`、`file_passive`、`deserialization_passive` 、`auth_session_passive`、`disclosure_passive`、`configuration_passive`、`crypto_passive`、`supply_chain_passive`、`business_logic_review`、`other_web_passive`、`race_condition_review`、`memory_safety_passive` 和 `dos_passive`。基线检查读取 GET 响应中的 MIME、CSP、HSTS 策略及私钥、调试堆栈、数据库错误标记；身份对比只产生需要人工确认的线索。`injection_errors` 仅被动匹配原有匿名 GET 响应中的 SQL、模板和命令解析错误，不修改 URL 或参数、不发送注入载荷，不验证可利用性。基线的数据库错误与该模板复用匹配器及去重标识。文档示例也可能命中，结果只作为待人工确认的线索。未命中不能解释为该类别安全。

## 添加一种实际测试

敏感信息、配置和加密模板分析已有响应，不读取额外敏感文件或破解密文；已识别的私钥和凭证格式在 HTTP 证据中脱敏。供应链入口只审查资源引用和组件线索，不连接漏洞数据库，也不能据版本信息声称命中 CVE。业务逻辑入口审查输入线索，需要业务规则和流程状态；竞争条件、内存安全与 DoS 仅分析已有运行诊断，不能确认可利用性，不会触发并发业务操作、崩溃或服务压测。

XXE、文件、反序列化和认证/会话模板只分析现有匿名响应中的异常、声明、输入及 Cookie/认证属性；不解析外部实体、不上传或读取额外文件、不构造或加载序列化对象、不尝试登录或破解会话。外部实体被拒绝等错误也可能说明防护已生效；Cookie 配置需要结合 HTTPS 和实际用途判断。线索不是可利用漏洞结论。

`role_compare` 已增强为匿名与专用账号逐对比较成功响应，同角色不同账号也参与比较。只把匹配身份对的证据关联到线索，不把其他身份的拒绝响应归入该线索。它不修改资源标识、不枚举其他用户资源，无法取代资源归属和权限矩阵的验证。

新增 `xss_passive`、`csrf_passive`、`ssrf_passive` 三个可单独选择的模板，复用原有匿名 GET 请求及 HTTP 证据：静态分析脚本来源与危险操作、表单与 Cookie 防护线索、服务端请求错误与地址输入线索。它们不执行脚本、不提交表单、不修改参数、不发起回连或内网请求，无法确认反射/存储型 XSS、服务端 CSRF 校验或 SSRF 可利用性。结果保持待人工确认，不适用与无法确定单独记录；没有线索不代表安全。DeepSeek 自动流程默认只选择基线，可由用户显式选择其他只读模板；模型只能安排用户选择与确定性策略共同允许的模板。

1. 定义具体规则的输入、适用条件、风险、最小证据和验证局限。先写正例、安全对照和不适用场景测试；不能只把类别名称当作检测能力。
2. 同步修改 `JobInput` 的确定性白名单、任务执行分派和目录。不得从模型、页面或导入文档加载脚本、命令或动态执行插件。
3. 所有请求继续经过执行网关。逐次校验精确主机、端口、路径、DNS/IP、授权有效期及绑定的授权版本，遵守禁止路径、停止开关、请求预算与时长限制；不得为新规则另建网络出口。
4. 保存规则标识、检查结果、请求与响应证据及关联关系。证据遵循统一脱敏、截断与凭据保护策略；历史证据缺少某项内容时明确标记，不能补写为已检查。
5. 新增边界拒绝、授权变更、超预算、停止、数据脱敏及报告追溯测试后再开放选择。报告区分线索与已验证结论，模型只能提出建议，不能改变执行策略。

首版仍仅执行受控只读请求。业务写入需要另行实现绑定请求内容、单次有效且避免重复执行的审批能力后才可开放；破坏性操作、任意代码执行和服务压测不提供执行能力。DoS 与竞争条件的诊断线索入口不表示提供压测或并发写入能力。

测试账号只使用专用账号与合成数据。证据在本地保存不等于允许发送给云模型；模型出口继续只接收经过脱敏与预览的必要内容，不能把新增请求/响应原文自动加入模型上下文。


## 受控主动验证与多轮流程

新增 `cors_verify` 和 `access_verify`，仍由统一网关逐次检查授权、范围、DNS、停止状态与预算。

- CORS 对照：同一接口发送 3 次匿名 GET（基线与两个固定 `.invalid` Origin），比较来源反射和凭据许可；不读取其他来源的数据，也不运行浏览器脚本。
- 权限对照：手动选择一个接口、允许身份和应拒绝身份（可以匿名），共发送 2 次 GET。需要预先约定合成数据的顶层 JSON 字段和期望值；前端仅提交值的 SHA-256，证据隐藏该字段值。允许身份先作为正向对照，不枚举资源、不修改资源标识。
- 对照行为复现仍为待人工确认，需要结合实际业务规则和浏览器条件评估影响；失败、截断和重定向不视为通过或已验证。

自动流程允许 1–3 轮，默认 2 轮。每轮只能选择已登记、无查询参数、可执行的 GET 接口及用户启用的只读模板。权限对照需要用户提供规则，暂不加入自动流程。模型只收到接口编号、方法、剩余预算和结构化检查状态；不自动发送接口网址、响应原文、账号或凭证。

累计请求上限包含接口发现和所有轮次任务。模型费用按配置的价格上界分轮预留，预留不等于实际账单；失败调用不会自动重试。重复的接口与模板组合、无新证据、达到轮数或预算、授权变化和停止操作都会终止后续执行。

任务详情展示覆盖统计、测试理由、验证条件、各次请求及关联证据。自动流程可下载完整 Markdown 报告，其中保留所有轮次的任务证据和停止原因。无检查明细或未发送请求的接口不会被标记为已通过。
